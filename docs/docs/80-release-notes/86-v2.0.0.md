## 🚨 Breaking Changes {#breaking-changes}

### `ProjectConfig` Moves to the Kargo Database {#projectconfig-database}

Kargo v2.0 stores `ProjectConfig`s in a PostgreSQL database instead of as
Kubernetes resources. This has several consequences for anyone upgrading.

* **A PostgreSQL Database Is Required**:
  The Helm chart refuses to render unless you either enable the bundled
  PostgreSQL (`database.postgres.enabled`) or point Kargo at your own server
  (`database.external.secretName`).

* **Existing `ProjectConfig`s Are Imported Once, Then Become Read-Only**:
  The first time the API server starts after the upgrade, it automatically
  imports every existing `ProjectConfig` resource into the database. This
  happens once. Afterwards, the `ProjectConfig` resources that remain in your
  cluster are read-only leftovers. A `ValidatingAdmissionPolicy` named
  `kargo-projectconfigs-read-only` rejects attempts to create or update them,
  although deleting them is still allowed. From now on, manage `ProjectConfig`s
  with the Kargo CLI (for example, `kargo apply -f` and
  `kargo get projectconfig`), the UI, or the API. Do not use `kubectl` or a
  GitOps agent such as Argo CD. If a GitOps tool currently syncs `ProjectConfig`
  resources into your cluster, those syncs will start failing.
  `kubectl get projectconfigs` no longer reflects the live configuration.

* **Do Not Change `EXTERNAL_WEBHOOK_SERVER_BASE_URL` During the Upgrade**:
  Webhook receiver URLs are derived in part from this setting. Changing it as
  part of the upgrade changes the URLs, and any webhooks you have already
  registered with external services will stop reaching Kargo.

* **Keeping a Namespace No Longer Keeps the `ProjectConfig`**:
  When a `Project` carrying the `kargo.akuity.io/keep-namespace` annotation is
  deleted, its `Namespace` is still retained, but its `ProjectConfig` is now
  deleted along with it.

* **`API_SERVER_ADDRESS` Is Now Required by More Components**:
  The controller, the management controller, the Kubernetes webhooks server,
  and the external webhooks server now all need to reach the API server, so
  each requires `API_SERVER_ADDRESS`. By default, the chart sets this for you
  when `api.enabled` is `true`. If you set `api.enabled` to `false`, set
  `controller.apiServer.address`, `managementController.apiServer.address`,
  `webhooksServer.apiServer.address`, and
  `externalWebhooksServer.apiServer.address` yourself. This includes sharded
  controllers running in other clusters, which now need both network access to
  the API server and credentials for it. If the API server is unavailable,
  `Stage` reconciliation stalls until it returns. If `api.tls.enabled` is
  `true` and `api.tls.selfSignedCert` is `false`, these components reach the
  API server at `https://kargo-api.<namespace>.svc` by default. Only the
  controller can be given extra CA certificates to trust (through
  `controller.cabundle`). For the management controller, the Kubernetes
  webhooks server, and the external webhooks server, your API server
  certificate must include `kargo-api.<namespace>.svc` as a subject
  alternative name and be signed by a certificate authority they already
  trust. Otherwise, set their `apiServer.address` to an address whose
  certificate they do trust.

* **Webhook Deliveries May Fail Briefly During the Upgrade**:
  During the rolling upgrade, new external webhooks server pods may reach API
  server pods that do not yet serve the route they use to find a webhook
  receiver, so some webhook deliveries may fail for a short time. Senders
  that retry failed deliveries recover on their own. Others, such as GitHub,
  do not retry; redeliver any failed deliveries from the sender if needed.

* **A `ProjectConfig` Follows Its `Project` by Name**:
  If you rebuild or restore your cluster while keeping the existing database,
  the `Project`s come back with new UIDs (backup tools such as Velero do not
  preserve them). Each `ProjectConfig` is kept and carried over to the restored
  `Project` of the same name. Its webhook receivers keep their URLs as long as
  the `Secret`s they reference are restored unchanged. A `ProjectConfig` is
  deleted only when Kargo observes its `Project` being deleted. As a result, a
  `Project` that is deleted and recreated under the same name while the
  management controller is not running, or before it has processed the
  deletion, inherits the previous `Project`'s `ProjectConfig`. Delete that
  `ProjectConfig` if it is not wanted.

* **Kubernetes 1.30 or Later Is Required**:
  The read-only protection described above relies on `ValidatingAdmissionPolicy`,
  which is generally available as of Kubernetes 1.30.

* **The First API Server Start May Take Longer**:
  Because the one-time import runs before the API server begins serving, its
  first start after the upgrade can take noticeably longer, especially with
  many Projects. The API server's startup probe allows about 15 minutes by
  default. See `api.probes.startupProbe` in the chart's values if you need to
  adjust this.
